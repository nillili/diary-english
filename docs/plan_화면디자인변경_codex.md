# 화면 디자인 변경 계획 검토

## 검토 요약

2026-10-12 기준 원본 계획과 현재 소스를 대조했다. 다크 집중 테마를 QSS로 적용하는 방향은 유지할 수 있다. 다만 라디오 버튼의 비활성 상태를 디자인 결함으로 오인할 가능성, 테마를 적용하지 않는 기존 UI 테스트, 파일 전체를 복원하는 되돌리기 절차를 우선 보완해야 한다.

이번 검토는 정적 코드 확인이다. 화면을 실행해 시각적 결함을 확정하거나 원본에 기록된 110개 테스트 통과를 재검증하지 않았다. 실제 화면 승인은 남아 있다.

## 제작자 의도와 고정 조건

- 사용자가 선택한 B 다크 집중 테마를 유지한다.
- 버튼 위치, 탭, 단축키, 문구, 상태 규칙과 현재 문장 표시 방식을 유지한다.
- 신규 색·모양은 QSS 한 파일에 모은다. 새 배지·아이콘·테마 전환 설정을 추가하지 않는다.
- 단계별 사용자 확인과 미확정 디자인 선택을 존중한다. 이번 검토에서는 앱 코드를 변경하지 않는다.
- 커밋과 푸시는 각각 별도 지시를 받는다.

## 우선순위별 문제와 채택 해결책

### F-001 · 높음 — 라디오 버튼의 선택 상태와 사용 불가 상태를 구분해야 한다

**근거:** 원본 3장 2단계는 흐릿한 동그라미를 선택 표시 문제로 다룬다. 하지만 `settings_tab.py::_sync_gender_radios()`는 확인된 성별 음성이 없으면 해당 버튼을 비활성화한다. `services/fakes.py::FakeSpeech.list_voices()`는 성별이 `unknown`인 음성만 반환하므로 안내된 `--dev-fake` 실행에서는 남녀 버튼 모두 비활성·미선택이다. `tests/test_ui.py::test_gender_radios_disabled_without_verified_voices`도 이를 확인한다.

**영향:** checked 색만 바꿔도 개발 모드 화면에서는 개선이 보이지 않는다. 비활성 버튼을 활성 버튼처럼 강조하면 선택할 수 있다는 오해가 생긴다.

**채택 해결책:** 먼저 실제 관찰 상태를 enabled/disabled와 checked/unchecked로 나누어 기록한다. 사용자가 색을 승인하면 QSS에서 이 조합을 구분한다. 성별 지원 판정은 유지하고, 활성·선택 상태는 별도의 임시 UI 확인 환경에서 재현한다.

**담당·시점:** 구현자가 2단계 수정 전에 상태를 확인하고, 사용자가 해당 상태의 시안을 승인한다.

**비용·잔여 위험:** 확인 환경 준비가 필요하며 실제 음성 지원 문제는 이 작업으로 해결되지 않는다.

**완료 기준:** 개발 모드의 미지원 버튼은 계속 선택 불가이고, 확인용 활성 버튼에서는 선택 여부가 식별된다. 마우스 진입만으로 비활성 버튼이 활성처럼 보이지 않는다.

### F-002 · 높음 — 기존 테스트 통과로 테마 영향 없음이라고 결론 내릴 수 없다

**근거:** 원본 2장의 “UI 테스트는 색을 보지 않으므로 영향 없음”과 달리, `tests/test_ui.py::ui`는 `MainWindow`를 직접 생성하고 `__main__.py`의 QSS 로딩을 실행하지 않는다. QSS에는 글꼴 크기, padding, min-width가 있고 `study_tab.py`는 입력창 높이를 고정한다.

**영향:** 기존 테스트가 통과해도 테마 적용 후 글자 잘림, 버튼 폭 증가, 입력창 표시 줄 수 감소를 놓칠 수 있다.

**채택 해결책:** 원본의 결론을 “기존 기능 테스트 통과, 테마 적용 화면은 미확인”으로 바꾼다. 현재 창 크기에서 실제 테마를 적용한 화면을 확인하고, 기존 UI 테스트 중 입력창 높이·행 배치·단축키 관련 검증도 QSS 적용 환경에서 실행한다. 테스트 종료 시 스타일을 복원하여 다른 테스트에 영향을 주지 않는다. 장식 규칙 자체를 복제한 테스트는 추가하지 않는다.

**담당·시점:** 구현자가 1단계 승인 전에 확인 결과를 준비하고 사용자가 화면을 확인한다.

**비용·잔여 위험:** 자동 기능 검증과 시각 검증이 모두 필요하다. 다른 화면 배율과 대체 글꼴 환경은 별도 확인 없이는 보장하지 않는다.

**완료 기준:** 한글·긴 경로·긴 번역문에서 핵심 조작 요소가 잘리지 않고, 입력창의 약 4줄 표시와 R·Space 범위가 유지된다. 사용한 글꼴·배율을 기록한다.

### F-003 · 높음 — 되돌리기 명령이 다른 미커밋 변경까지 지울 수 있다

**근거:** 원본 6장은 `git checkout --`로 `__main__.py`와 `pyproject.toml` 전체를 복원한다. 이는 테마 관련 부분만 취소하는 절차가 아니다. 원본 1장의 QSS 제거 원칙은 현재 `THEME_FILE.exists()` 조건과 부합하지만 재시작이 필요하다.

**영향:** 이후 동일 파일에 추가된 다른 작업까지 잃을 수 있다. 실행 중 QSS 파일을 삭제해도 이미 적용된 화면은 즉시 복원되지 않는다.

**채택 해결책:** 화면만 되돌릴 때는 QSS를 백업 이름으로 옮기고 앱을 재시작한다. 코드까지 되돌릴 때는 diff를 확인해 테마 로딩과 package-data 변경만 제거한다. 커밋 이후 revert는 테마만 포함한 커밋임을 확인한 경우에 사용한다.

**담당·시점:** 구현자가 다음 수정 전에 되돌리기 안내를 교체한다.

**비용·잔여 위험:** 부분 복원은 diff 확인이 필요하다. 기본 모습은 OS·Qt의 기본 스타일을 의미하며 항상 밝은 테마라는 뜻은 아니다.

**완료 기준:** 테마 제거 후 재시작이 성공하고 다른 미커밋 작업과 사용자 데이터가 유지된다.

### F-004 · 중간 — 화면 확인 항목에 상태와 재현 절차가 부족하다

**근거:** 원본은 세 탭의 읽기, 표 선택, 메시지 창을 언급하지만 키보드 포커스와 콤보박스 팝업을 포함하지 않는다. `theme.qss`의 명시적 focus 규칙은 일기 입력창에만 있다. `library_tab.py`는 행 클릭 시 바로 학습 화면으로 이동한다.

**영향:** 빈 화면만 확인하면 선택 배경, 팝업 항목, 포커스 식별 문제를 놓친다. 표를 클릭한 직후 화면이 바뀌므로 선택 색을 확인하기도 어렵다. 이는 결함 확정이 아니라 검증 공백이다.

**채택 해결책:** 개발 모드에서 가짜 일기 변환·저장으로 표 데이터를 만들고, 행 클릭 후 보관함으로 돌아와 선택 상태를 확인한다. 콤보박스 펼침, Tab 이동, 활성/비활성 버튼, 번역문과 표현 예시, 미저장 확인 창을 체크리스트에 넣는다. 문제를 확인한 항목만 사용자 확인 후 수정한다.

**담당·시점:** 구현자가 1단계 확인 전에 체크리스트 초안을 만들고 사용자 확인 결과를 기록한다. 최종 색 반영은 2단계 승인 후다.

**비용·잔여 위험:** 수동 확인 시간이 늘지만 미확인 위젯까지 일괄 스타일링할 필요는 없다. 네이티브 파일 선택 창은 기존 제외 범위를 유지한다.

**완료 기준:** 포커스 위치, 선택 항목, 비활성 상태를 서로 구분할 수 있고 메시지 창의 모든 기존 버튼과 문구가 읽힌다. 실제 API 키나 개인 일기는 확인용 자료로 쓰지 않는다.

### F-005 · 중간 — 색 단일 관리 원칙과 현재 구현의 예외가 명시되지 않았다

**근거:** 원본 2장의 색 표에는 QSS의 `#242c38`, `#7a8696`, `#1f6f5c` 등 여러 색이 빠져 있다. `study_tab.py::examples_html()`에는 기존 `style='color:gray'`가 남아 있다. 따라서 “색·모양 전부”가 QSS에 있다는 설명은 현재 구현과 일치하지 않는다.

**영향:** 팔레트만 수정하면 모든 글자색이 바뀐다고 오해할 수 있으며 표현 예시의 가독성이 누락될 수 있다.

**채택 해결책:** 색 표에 실제 QSS 색과 용도를 맞춰 기록한다. 기존 표현 예시의 인라인 색은 이번 범위의 예외로 명시하고 실제 가독성을 확인한다. 이를 옮기는 Python 수정은 현재 범위에 자동 포함하지 않는다.

**담당·시점:** 구현자가 3단계 문서 정리 때 반영하고, 표현 예시 가독성은 1단계 화면 확인에 포함한다.

**비용·잔여 위험:** 색 표와 QSS를 함께 유지해야 한다. 표현 예시가 읽기 어렵다면 해당 부분의 별도 수정 승인이 필요하다.

**완료 기준:** 사용 색의 누락과 관리 범위의 오해가 없고, 표현 예시 확인 결과가 기록된다.

## 구현 전에 확정할 사항

- 구현자: 라디오 버튼의 현재 enabled/checked 상태를 먼저 확정한다. 이후 사용자에게 해당 상태의 색을 선택받는다.
- 사용자: 표 선택 색과 글자 크기는 데이터가 채워진 실제 화면을 보고 2단계 전에 결정한다. 현재 입력창은 15px이며 공통 14px·번역창 17px와 구분해 안내한다.
- 원본 5장의 미래 밝은 테마 질문은 현재 작업의 선행 조건에서 제외한다. 지금은 QSS 제거·재시작으로 기본 스타일 복귀만 보장한다.
- 구현자: 테마 파일 읽기 실패는 현재 시작 단계 예외로 이어질 수 있음을 기록한다. 실패 시 기본 스타일로 실행하고 원인을 로그에 남기는 보완은 Python 수정 범위를 사용자에게 제시한 뒤 결정한다. 이 선택은 배포 전 확정한다.

## 새로운 아이디어

### N-001 — 동일 데이터로 세 탭의 확인 화면 보관

개인정보 없는 가짜 일기와 동일한 창 크기를 사용해 승인된 화면을 보관하면 다음 수정 때 비교하기 쉽다. 자동 이미지 비교 체계를 도입할 필요는 없으며, 사용자 화면 승인 시점에만 기록한다.

## 의도를 벗어난 아이디어

### OUT-001 — 밝은/어두운 테마 전환 기능

설정 항목 추가 금지와 QSS 한 파일 원칙을 넘어선다. 미래 가능성만으로 두 테마를 준비하지 않으며 별도 요청이 있을 때 다룬다.
